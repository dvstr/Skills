# PRD - Epic Name

# Introduction

One-liner and goal – what we want to change and the purpose behind doing it.

# Context and Problem

## Target Audience

For whom this change is intended and the proportion of such users.

## Problem Statement

"Current State vs. Future State" – a brief description of the problem, how users currently solve it, and how we envision the solution.

# Business Requirements and Success Criteria

## Goals

A table of goals – what we want to achieve and what we consider success. By what metrics will we track this?

| **Goal**                           | **Metric**                                  |
| ---------------------------------- | ------------------------------------------- |
| e.g., Simplify the user experience | e.g., Customer satisfaction score increases |
| Goal 2                             | Metric for goal 2                           |

## BPMN Diagram

- link to the BPMN diagram (place as a child document to the PRD)

## Business Requirements

A set of business requirements that must be implemented and taken into account. How user scenarios should change after the solution is implemented.

## Constraints / Compliance / Non-Functional Requirements

Any limitations, regulatory requirements, and non-functional requirements (NFRs) to be considered during the implementation of these changes (e.g., security rules, audit logging, data retention, availability).

# Scope

## In Scope

The set of planned functional changes.

## Out of Scope

What will not be included in the current implementation.

# Dependencies and Impacts

Which other teams will be involved and what will be required from them. Are there external dependencies (partners/vendors, legal, marketing, ops)? Does anything need to be anticipated for Customer Support / Call Center (JSM requests, scripts, FAQs, trainings), etc.?
